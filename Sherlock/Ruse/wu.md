* **Given:** a directory named `ireks-Mac_20250308_160413`
* **Description:** An organization's macOS system was compromised after an attacker gained initial access through a disguised entity. The intrusion escalated privileges, established persistence, and enabled unauthorized remote access. You have been hired as a forensic analyst to examine the provided artifacts and reconstruct the attacker's actions.
* **Hints:**
    * No hint is given.

### 2. Investigation ###
#### First Analysis ####
Before diving into the forensic artifacts, we need to understand the nature of the evidence. Based on the directory naming convention (`<Hostname>_<YYYYMMDD>_<HHMMSS>`) and the presence of processed logs alongside raw directories, this artifact represents a **macOS Forensic Triage Collection**

Our collection comes from a host named **ireks-Mac**, captured on **March 8, 2025,** at **16:04:13**. Here is the breakdown of the evidence structure:

![](pic1.png)

![](pic2.png)

> * **Root Directory**:
>   * `ireks-Mac-Triage`: This is the main folder containing the collected macOS forensic artifacts.
>   * `Full_file_listing.txt`: List of all files present on the target system.
>   * `ireks-Mac_20250308_160413_File_Hashes.txt`: Cryptographic hashes of collected files to verify data integrity.
>   * `ireks-Mac_20250308_160413_Processing_Details.txt`: Execution logs generated by the triage tool during collection.
> * Inside **ireks-Mac-Triage**:
>   * `fsevents`: File System Events logs. Tracks file creation, modification, and deletion over time.  
>   * `Library`: System-wide settings and application data. A common location for malware persistence (e.g., LaunchDaemons).
>   * `private`: Contains core,hidden macOS directories like `/etc` (configs), `/var` (logs), and `/tmp` (temporary files).
>   * `spotlight`: Spotlight search index data. Useful for finding what the user searched for and accessed.
>   * `System`: Core macOS operating system files and binaries.
>   * `UnifiedLogs`: The modern macOS Unified Logging system. Crucial for analyzing system, application, and security events.
>   * `Users`: User profiles. Contains personal documents, browser history, downloads, terminal history, and user-level persistence (~/Library).

#### Task 3 ####
```text
When did the user first initiate the download of that malicious entity (UTC)?
```

The command `plistutil` also revealed a key named `DownloadEntryDateAddedKey` which handles the time when the system starting downloading time of a entity, these are some important keys when download a file from the Internet saved in `Downloads.pslist`:
> * `<key>DownloadEntryPath</key>`: The absolute file path where the downloaded item is saved on the local disk
> * `<key>DownloadEntryDateAddedKey</key>`: The exact timestamp when the download entry was initiated and added to the queue (UTC)
> * `<key>DownloadEntryProgressBytesSoFar</key>`: The total number of bytes successfully downloaded before the process completed or stopped
> * `<key>DownloadEntryURL</key>`: The direct source URL from which the file was downloaded.
> * `<key>DownloadEntryQuarantineProperties</key>`: A dictionary containing security metadata used by macOS Gatekeeper, including the originating URL, referrer URL, and the specific application responsible for the download.

By the way, the answer for the question is: `2025-03-07 21:11:56`. 

#### Task 4 ####
```text
What was the timestamp (UTC) of the user's most recent interaction with the malicious file?
```
This question is the starting point of a list of the trickiest questions in this Sherlock challenge. To make it clear, the question only asks `most recent interaction`, not any specific action such as `delete`, `run`, `move`, ... so the investigation's range is such a wide one, which makes it harder to find out the solution.

At first, I went down several false paths. My initial thought was that the answer should still come from `Downloads.plist`, because it already gave the exact timestamps for the first and second downloads. That line of thinking quickly became weak, since `downloaded` does not necessarily mean interact.

The second false lead was `History.db`, where I could clearly see the victim revisiting the Google Drive page. However, those timestamps only proved that the page was opened again, not that the malicious app itself was touched afterward.

I also checked artifacts such as quarantine events and recently used application traces, but those either pointed to the download/first-open stage or did not provide a clean enough timestamp to confidently call it the final interaction. So, after ruling those out, I shifted the focus to actual execution traces instead.

After checking multiple artifacts such as Safari history, quarantine events, and recent applications, the most reliable trace turned out to be the `launchd` execution log:

> `var/log/com.apple.xpc.launchd/launchd.log`: is the log file for launchd, which is macOS's process manager and init system.
>  It records many types of highly valuable forensic events, such as:
>  * which processes were spawned
>  * which services were enabled, disabled, or bootstrapped
>  * which user sessions were created
>  * which applications were launched through launchd or xpcproxy
>  * which daemons or agents crashed, exited, or restarted
>  * events related to LaunchDaemons, LaunchAgents, and XPC services
> 
>  * It's useful because many actions on macOS do not appear directly in shell history, but they still have to pass through `launchd`, so activities often leave traces here:
>      * opening an app
>      * enabling SSH
>      * spawning systemsetup
>      * running sysadminctl
>      * creating user/502
>      * launching persistence
>  
>  * A quick walkthrough to understand it:
>      * `(pid/1111 [sysadminctl]) <Notice>`: created means the sysadminctl process was just created
>      * `(system) <Notice>`: Enabling service com.openssh.sshd means the SSH service is being enabled
>      * `(user/502) <Notice>`: created means the bootstrap domain for user UID 502 was just created, usually associated with user creation or user logon
>      * `Bootstrap by launchctl ... succeeded`: means the service was successfully loaded
>      * `Successfully spawned X because ...`: means the process or service X was actually launched successfully

![](pic13.png)

In this triage, I find 3 logs, however, after cross-referencing with the timeline in previous artifacts, the most valuable one is:

```text
ireks-Mac-Triage/private/var/log/com.apple.xpc.launchd/launchd.log.2
```

I found the latest successful spawn event for `Scientific-Calculator`, which indicates the last time the malicious application was actually interacted with by the user:

![](pic14.png)

The most recent relevant line shows the app being launched at `2025-03-07 23:14:37` local time. However, when I submitted, it did fail, why's that?

This happens because of the difference of timezone between the triage and the question. `private/var/localtime` and `private/etc/log/install.log` reveals the true timezone of the triage, which is `UTC+2`:

![](pic15.png)

![](pic16.png)

Since the machine was running in `UTC+2`, the converted UTC timestamp is:

`2025-03-07 21:14:37`

So the answer is: `2025-03-07 21:14:37`

#### Task 5 ####
```text
The attacker used a tool to drop files and bypass Gatekeeper. What is the name of the tool used for this technique?
```

This is another tricky question (for me).

(*Note: OSINT skill needed*)

> **Gatekeeper:** A built-in security mechanism that enforces application whitelisting and code-signing verification. Gatekeeper intercepts the first-time execution of downloaded binaries. It validates their cryptographic signatures and Apple Notarization status to ensure the software originates from a trusted developer and has not been altered.

Normally, Gatekeeper can be bypassed by the terminal command:

```bash
xattr -dr com.apple.quarantine /path/to/Application.app
```

However, when I found all evidences in `Users/irek/.zsh_sessions`, where save the command history of user `irek`, there are none helpful information:

![](pic17.png)

So I decided to realize a small research on the Internet, after scrolling a bit, I found [this article](https://unit42.paloaltonetworks.com/gatekeeper-bypass-macos/):

![](pic18.png)

The article shows detailed information about how some tools fail to apply the `com.apple.quarantine` attribute to extracted or downloaded files, allowing untrusted binaries to completely bypass Gatekeeper. Inside, there's a part catch my eye:

![](pic19.png)

It shows that some unix based tools used to download third-party applications cannot be marked as quarantined by Gatekeeper, including `curl` - a tool can be used to download any payloads directly via the terminal. 

Therefore, the answer is: `curl`.

#### Task 6 ####
```text
What is the full file path of the Mach-O executable crafted by the attacker for privilege escalation?
```

Back in `irek/.Trash`, I found a suspicious executable named `expooo` alongside `overwrite_file.bin`, `race.zip`, and `switch_race.c` which strongly indicates these are tools for a chain of privilege escalation, and the `expooo` is a Mach-O binary:

![](pic20.png)

*(Note: `/Users/irek/.Trash/expooo` was not the answer here)*

The chain was quite clear:
1. Through the reverse shell established by initial payload `Scientic-Calculator`, the attakers abused `curl` to download a `race.zip` file from their server.
2. After extracting the achive, they obtained `switch_race.c` and compiled it to craft the final Mach-O executable `expooo`.

![](pic21.png)

Uploading the `expooo` binary to [VirusTotal](https://www.virustotal.com/), I could put all puzzles together to complete the picture:

![](pic22.png)

The CVE exploited is `CVE-2022-46689`, the uploaded `switch_race.c` source code is a local privilege escalation exploit leveraging the `MacDirtyCOW` vulnerability. There's a available MacDirtyCOW [PoC](https://github.com/zhuowei/MacDirtyCowDemo) that matches with our case here:

![](pic23.png)

> * **How it works:** The binary `expooo` accepts two arguments: a target system file to overwrite and an exploit payload. It initiates a race condition by spawning a secondary thread `switcheroo_thread` that toggles a specific memory mapping `ctx->e0` between Read-Only (RO) and Read-Write (RW) permissions every 100 microseconds using `vm_map`. Simultaneously, the main thread triggers `vm_read_overwrite`. This forces the XNU kernel to write the attacker's payload directly into the target file's page cache before the Copy-on-Write (COW) mechanism can safely isolate the memory, resulting in an unauthorized permanent file overwrite on the disk to obtain root privileges.

The picture is brighter, now how can we find the first absolute path of `expooo`? 

I marked that this user `irek` only has 5 folders: `.Trash`, `.zsh_sessions`, `Desktop`, `Documents`, `Library`. Here I only suspected `Desktop`, `Documents`, and `Library`, since the others are not common places for attackers to exploit.

However, 2 of them `Desktop` and `Documents` (even `Downloads` if it appears) have a secure mechanism named **TCC** (Transparency, Consent, and Control). This mechanism will check if a file has `kTCCServiceSystemPolicy<Folder_Name>Folder` permission, which allows the file to read/write in that folder. Since we all know `expooo` is crafted then ran to escalate privileges, the system may spawn a log record to check its permission in `TCC.db`:

```text
ireks-Mac_20250308_160413/ireks-Mac-Triage/Users/irek/Library/Application Support/com.apple.TCC/TCC.db
```

I used `DBrowser for SQLite` to open the database, and in the very end row, our hypothesis is checked:

![](pic24.png)

So the answer is: `/Users/irek/Desktop/expooo`

#### Task 8 ####
```text
During the privilege escalation phase, the attacker mimicked the use of a well-known system file by altering a specific word in its configuration, enabling them to gain a root shell. Based on the comparison between the original file and the modified file, what is the specific word that was changed to facilitate this exploit?
```

As the PoC indicates, this malicious payload `overwrite_file.bin` is used by `expooo` to inject an original system file:

```bash
# su: auth account session
auth       sufficient     pam_permit.so 
auth       required       pam_opendirectory.so
account    required       pam_group.so no_warn group=admin,wheel ruser root_only fail_safe
account    required       pam_opendirectory.so no_check_shell
password   required       pam_opendirectory.so
session    required       pam_launchd.so
``` 
 
This contains a modified version of the PAM (Pluggable Authentication Modules) configuration for `su`. Comparing the original system file against the malicious replacement shows that the attacker replaced the usual PAM module reference with a more weak one:

![](pic25.png)

![](pic26.png)

* original behavior: `pam_rootok.so`
* modified behavior: `pam_permit.so`

With `permit`, the attacker instructed the system to grant authentication success to anyone running `su`, without asking for password.

So the answer is: `permit`

#### Task 9 & Task 18 ####
```text
After gaining root privilege, the attacker created a new user, when did he create that user (UTC)?

The legitimate user noticed and deleted the unauthorized account created by the attacker. When did the user initiate the deletion of the attacker-created account (UTC)?
```

As I mentioned above, to create a new user via terminal, the attackers often use `sysadminctl`, which will be supervised by one of the `launchd.log`. In this case, after getting root, the same thing happened. So the most useful artifact again is:

```text
ireks-Mac-Triage/private/var/log/com.apple.xpc.launchd/launchd.log.2
```

Inside this file, I found the `sysadminctl` process being created at around `2025-03-07 23:27:57`, in UTC, this means `2025-03-07 21:27:57`, however this is not the answer.

![](pic27.png)

So now we need another stronger artifact to prove the existence of the new user created by the attacker. And what can be stronger than that user directory itself, the `Deleted-User` one:

![](pic28.png)

Inside, there's only one artifact left: `loki.dmg`. This happens since the victim acknowledged his machine has been hacked and he tried to delete the suspicious user (in Task 2 I mentioned this information).

> `.dmg` file (Apple Disk Image): a digital container used primarily by the macOS operating system, it's functionally similar to an `.iso` file on Windows.
> `.dmg` created in 4 circumstances: 
>   1. Cloning/Backup-ing a disk/ directory.
>   2. Encrypted information
>   3. Created by developpers to distribute application
>   4. Delete an user (our case)

This file metadata and contents can be read by `7z l`:

```bash
7z l ireks-Mac_20250308_160413/ireks-Mac-Triage/Users/Deleted-Users/loki.dmg
```

![](pic29.png)

![](pic30.png)

The discrepancy between `sysadminctl` process in launchd log and metadata of `loki.dmg` can be comprehended that the attackers actually finish their bash command using `sysadminctl` to create another account at `21:27:57`. However, the system needs to boot up others process before really creating the new user directory, and only until `21:28:01` that `loki` is finished creating.

So the answer is: `2025-03-07 21:28:01` for Task 9 and `2025-03-08 07:58:55` for Task 18

#### Task 14 ####
```text
The malicious file created a specific file to ensure the malware runs every time the user logs into the system. What is the name of this file?
```

As the information provided by `VirusTotal`, this type of malware often creating fake `LaunchDaemon`/`LaunchAgent` plist file. By examining the user folder, I found the malicious LaunchAgent:

`com.appule.sysetmd.plist`

The typo in the name `appule` and `sysetmd` is the masquerading technology as `apple` and `systemd` (macOS uses `launchd` not `systemd` like Linux btw).

So the answer is: `com.appule.sysetmd.plist`
